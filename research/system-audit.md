## Existing capabilities (before this work)

- **Sensor pipeline** (`src/core`): unit conversion, stand-still calibration, complementary filter, segment and joint angles, hysteresis repetition detector, SPARC, per-repetition and per-step metrics. Every session stores its `algorithmVersion`.
- **Sessions** (`src/session`): live engine; raw frames stored for live sessions (`hasRaw`); demo history generated by the same engine from virtual patients (simulated, labelled).
- **Research module** (`src/research`, `features/research`): goniometer validation sessions, Protocol Studio (versioned and immutable), agreement statistics (Bland–Altman, ICC, SEM/MDC), datasets, capability map.
- **Functional Progression System** (`src/rehab`): goals, versioned programs, practice records with minutes (the dose source used here), studies with ethics and consent gates, movement metric definitions with validation status (`rehab/movement.ts`), pseudonymised study exports.
- **Sync and server:** an outbox in the same transaction as each write; PostgreSQL migrations with immutability triggers; audit log. Never verified against a live database (per the earlier engineering report).
- **Tests at baseline:** `tsc -b` ✅, `eslint .` ✅, `vitest run` **377 passed in 30 files** (run at the start of this work).

## Risks identified

- **Participant "codes" are first names in clinic use** (`data/models.ts`), so any export must pseudonymise. The new exports do.
- **Lab records need a schema upgrade.** It must be additive and tested; it was done as IndexedDB v4.
- **Real data.** No clinic data were available in this environment. All real-data paths are implemented and tested on simulated data with identical code.

## Decisions taken from the audit

1. Build on `rehab/movement.measureSession` (per-repetition metrics) and `core/*`; do not reimplement the pipeline.
2. Pure computational layer `src/lab` and a lazy UI chunk `features/motorlab`; no new services.
3. Local-only lab store in this version, with server sync documented as the next step.
4. The demo workspace is the labelled synthetic test bed; the clinic workspace never includes simulated data (enforced in `dataset.ts`, `readiness.ts`).
