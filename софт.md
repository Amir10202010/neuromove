Веб-приложение находится в `website/`, прошивка ESP32 — в `firmware/`, схемы и CAD-модели — в `hardware/`.

⚠️ **26 сентября 2026 — первая версия приложения готова: [`website/`](website/README.md).**
Этот документ сохраняет ранние требования из питча и может содержать прежние предположения;

Что обещано в питче и за что отвечает софт:

- базовый алгоритм — ROM, симметрия, плавность из сырых данных IMU;
- веб-интерфейс на компьютере с отчётом — хотя бы таблица и один график, PDF,

- демонстрация вживую: датчик на руке → движение → отчёт на экране в реальном времени;
- тест укладывается в 10–15 минут.

## 0. Как устроено

```
Датчики: IMU на туловище, плече, предплечье — шлют СЫРЫЕ числа, сами ничего не считают
   │
   ├── способ А: провода → ESP32 → USB, текст CSV, 100 Гц ───┐
   ├── способ Б: каждый блок по Bluetooth LE, 50 Гц ─────────┤
   └── способ В: блоки → хаб по ESP-NOW → USB ───────────────┤
                                                              ▼
   Лаборатория на Python (октябрь)           Веб-приложение в Chrome на компьютере (с ноября)
   запись, алгоритмы, проверка точности      датчики → калибровка → тест → отчёт → история
                                                              │
                                       хранение на компьютере → выгрузка CSV, отчёт в PDF
```

Три решения, на которых всё держится:

1. **Датчики шлют сырые числа, углы считает софт.** Поправил формулу — перепрошивать
   ничего не надо. Сырые данные остаются: по ним можно пересчитать все старые тесты
   и обучить ИИ.
2. **Один алгоритм: сначала Python, потом перенос на TypeScript.** Python — эталон,
   на нём проще отлаживать и проверять. Приложение проверяется на тех же записях:
   ответы должны совпасть.
3. **Один формат файла везде.** Запись лаборатории и выгрузка из приложения — одинаковый CSV.

## 1. Контракт с железом — согласовать с Санжаром на этой неделе

Единственное, о чём надо договориться. Дальше работаете независимо: ты — на симуляторе,
он — на стенде.

### Настройки датчика

- Акселерометр ±4 g: 8192 единицы = 1 g.
- Гироскоп ±1000 °/с: 32.8 единицы = 1 °/с. При заводских ±250 °/с быстрый взмах руки
  упрётся в потолок.
- Встроенный фильтр MPU-6050 (DLPF) — около 44 Гц.
- Магнитометр (если всё же BMX055) в версии 1 не передаём: в помещении он врёт.

### USB — способы А и В

Скорость порта 460 800 (была 921 600: 12 октября 2026 на маке с платой на CH340C на 921 600 шли каракули). При старте устройство печатает паспорт — строки с `#`, дальше одна
строка на отсчёт, целые числа прямо с датчиков. Столбцы названы по месту датчика:

```
# imu-csv v1
# device=NM-01 fw=0.1 rate_hz=100 acc_g=4 gyro_dps=1000 sensors=trunk,upper_r,fore_r
seq,trunk_ax,trunk_ay,trunk_az,trunk_gx,trunk_gy,trunk_gz,upper_r_ax,…,fore_r_gz
0,152,-40,8174,12,-35,7,98,15,8201,-4,20,11,…
```

`seq` — номер отсчёта, время = `seq / rate_hz`. Имена мест: `trunk` — туловище,
`upper_l`, `upper_r` — плечо, `fore_l`, `fore_r` — предплечье.

### Bluetooth LE — способ Б

- Имя блока: `NM-trunk`, `NM-upper_r`, … — по нему приложение понимает, где датчик.
- Свой сервис и характеристики. UUID сгенерировать один раз
  (`python3 -c "import uuid; print(uuid.uuid4())"`) и вписать **строчными буквами** в оба кода.

| Характеристика | Направление | Что |
|---|---|---|
| `data` | блок → компьютер, notify | пакеты с отсчётами |
| `control` | компьютер → блок, write | 1 — начать, 0 — остановить |
| `info` | чтение | версия прошивки и формата, частота, диапазоны |
| Battery Service, стандартный `0x180F` | чтение | заряд, % |

Пакет `data` — 18 байт, little-endian; стандартная полезная нагрузка BLE — 20 байт.

| Байты | Поле | Тип |
|---|---|---|
| 0–3 | `seq` — номер отсчёта этого блока | uint32 |
| 4 | номер места: 0 — туловище, 1 — плечо Л, 2 — плечо П, 3 — предплечье Л, 4 — предплечье П | uint8 |
| 5 | флаги: бит 0 — батарея садится | uint8 |
| 6–17 | ax, ay, az, gx, gy, gz | int16 × 6 |

Пропуск в `seq` — потерянный пакет, его видно и считаем.

**Синхронизация блоков.** У каждого блока свои часы, а угол в локте — это два блока
в один момент. Решение: в начале теста все блоки кладут вместе и один раз стукают
о стол. Всплеск ускорения виден во всех записях сразу — по нему время выравнивается.
В способах А и В синхронизация не нужна: часы одни.

Любая правка формата — новая версия (`v2`) в паспорте и в `info`.

**Дополнения внутри v1 — 2 октября 2026, прошивка стенда ([`firmware/`](firmware/README.md)).** Разбор
приложения их уже понимает, поэтому версия та же:

- паспорт и заголовок повторяются каждые 2 с — приложение подхватывает поток с любого места;
- свои пары в паспорте: `# board=esp32s3 i2c_hz=100000 arm=right`;
- поправки акселерометра из калибровки в 6 положениях: `# cal_fore_r=12,-30,45,10012,9988,10005` —
  ноль трёх осей в единицах датчика и масштаб × 10 000; поток остаётся сырым, поправки применяет приложение;
- строка `#` без знака `=` — сообщение человеку («перезапускаю шину»), приложение её пропускает;
- номер отсчёта = прошедшее время в отсчётах: плата не успела — номер всё равно растёт, назад не идёт.

### Паспорт записи

Всё о записи — в строках `#` в начале того же CSV: один файл, ничего не теряется.
`record.py` дописывает к паспорту устройства движение, сторону, код участника
(`V01` — доброволец, `P01` — ребёнок), кто мерил и дату. **Имён нет.**
Во время проверки точности клавиша в `record.py` ставит метку «гониометр показывает 90°» —
в файл ложится строка `# mark seq=1234 ref=90`.

### Углы — первая версия

Каждый датчик на каждом отсчёте знает, где у него «верх»:

- **акселерометр** видит гравитацию. Не уплывает со временем, но дёргается при каждом рывке;
- **гироскоп** даёт поворот. Гладко, но потихоньку уплывает.

Фильтр на каждом шаге поворачивает прошлый «верх» по гироскопу и на 2% подтягивает его
к акселерометру: гладкость одного без дрейфа другого. Из «верха» получается главный угол —
**подъём кости от положения «висит вниз»**. Он не зависит от плоскости: вперёд, в сторону,
по диагонали — считается одинаково.

```python
import numpy as np

def gravity_track(acc, gyro, fs, alpha=0.98):
    """Направление «вверх» в осях датчика на каждом отсчёте.
    acc  — массив (N, 3) в g; ось X датчика — вдоль кости, к кисти
    gyro — массив (N, 3) в °/с, смещение уже вычтено
    fs   — частота отсчётов, Гц"""
    dt = 1.0 / fs
    w = np.radians(gyro)
    g = np.empty_like(acc)
    g[0] = acc[0] / np.linalg.norm(acc[0])
    for k in range(1, len(acc)):
        # датчик повернулся на w·dt — «верх» в его осях повернулся навстречу
        pred = g[k - 1] - np.cross(w[k], g[k - 1]) * dt
        # 98% — предсказание по гироскопу, 2% — поправка по гравитации
        g[k] = alpha * pred + (1 - alpha) * acc[k]
        g[k] /= np.linalg.norm(g[k])
    return g

def elevation(g):
    """Подъём кости, градусы: 0 — висит вниз, 90 — горизонтально, 180 — вверх."""
    return np.degrees(np.arccos(np.clip(-g[:, 0], -1.0, 1.0)))
```

Проверено на синтетике 24 сентября 2026: подъём до 140° вперёд, в сторону и по диагонали,
с шумом и смещением гироскопа — средняя ошибка 0.2°, максимум 0.9°. В синтетике нет
рывков, поэтому на людях будет хуже — отсюда критерий ≤ 5° против гониометра.

⚠️ **26 сентября 2026: `arccos(−g_x)` заменён.** Формула верна, только если ось X датчика идёт
точно вдоль кости. Когда в симулятор добавили перекос крепления на 2–5° (ремешок никогда
не сидит идеально), ошибка на высоких углах доходила до 10°: вычитание угла калибровки
исправляет её только около нуля. В приложении подъём = угол между «верхом» сейчас и «верхом»
в позе калибровки (рука висит вдоль тела — значит, направление кости в осях датчика известно
точно): средняя ошибка 0.1–1.5°, пик ±3° при любом перекосе. Лаборатории нужна та же формула —
иначе golden-тесты Python и приложения не совпадут:

```python
def elevation_from_ref(g, g_cal):
    """Подъём от позы калибровки, градусы: угол между «верхом» сейчас и при калибровке."""
    return np.degrees(np.arccos(np.clip(g @ g_cal, -1.0, 1.0)))
```

| Что в отчёте | Как считаем |
|---|---|
| Подъём руки | `elevation` датчика на плече |
| Сгибание локтя | поворот в шарнире локтя: ось шарнира — ось Z датчика плеча (датчик снаружи плеча, Z — от кожи); «вниз» проецируется на плоскость шарнира, углы плеча и предплечья — со знаком (`website/src/core/pipeline.ts`, `elbowFlexion`). До 2 октября 2026 было `elevation(предплечье) − elevation(плечо)` — неверно, если плечо уходит назад или в сторону: до −41° без пометки (`website/docs/ENGINEERING_10H/FINDINGS.md`, F1) |
| Наклон туловища | `elevation` датчика на груди минус его значение при калибровке |

Сгибание локтя в любой позе требует общей 3D-ориентации двух датчиков (фильтр Madgwick,
библиотека `ahrs` для сверки). Решаем по данным: если на проверке ошибка больше 5° — переходим.
**Решено 2 октября 2026.** Независимый эталон показал ошибку больше 5° (F1), но полный 3D-фильтр
без магнитометра не знает взаимного поворота датчиков вокруг вертикали. Вместо него — шарнир:
ось сгибания локтя закреплена в плече, и её хватает, чтобы разложить движение со знаком.
Худшая ошибка объёма при плече, отклонённом до 20° в любую сторону, — 1,6° (модель); на станке
это проверяет шаг 6 `website/docs/ENGINEERING_10H/HARDWARE_ACCEPTANCE.md`. Ограничения — переразгибание
и вальгус с пронацией (F3, F4).

### Калибровка — перед каждым тестом

1. «Сидим прямо, руки вдоль тела, не двигаемся 3 секунды». Среднее гироскопа — смещение,
   его вычитаем весь тест. Углы в этой позе — нули.
2. Если в эти 3 секунды было движение (гироскоп выше порога) — повторить.

### Деление теста на повторы

```python
def count_reps(angle, low, high):
    """Повторение: угол ушёл выше high и вернулся ниже low.
    Два порога (гистерезис) — дрожание около одного порога не даёт ложных повторов.
    Возвращает список пар (начало, конец) — индексы отсчётов."""
    reps, state, start = [], "low", 0
    for k, a in enumerate(angle):
        if state == "low":
            if a < low:
                start = k            # последний момент в нижней зоне
            elif a > high:
                state = "high"
        elif a < low:                # были наверху и вернулись вниз — повтор готов
            reps.append((start, k))
            state, start = "low", k
    return reps
```

Пороги — доли от ожидаемого размаха: `low` = 20%, `high` = 80%. Размах берётся из прошлого
теста ребёнка или задаётся врачом. Проверено на синтетике с этими порогами: 10 повторов из 10.

### Метрики — `metrics.py`

| Метрика | Формула | Замечание |
|---|---|---|
| ROM | максимум угла в каждом повторе, в отчёт — медиана из трёх | медиана не даёт одному неудачному повтору испортить число |
| Симметрия | ROM слабой стороны / ROM сильной × 100% | «правая — 80% от левой», как на макете |
| Плавность | SPARC по профилю угловой скорости с гироскопа, на каждый повтор | формула — в статье Balasubramanian и др., 2015 (ссылка в `README.md`); проверить на синтетике: плавное движение даёт значение ближе к нулю, чем рваное |
| Компенсация | максимальный наклон туловища во время подъёма руки, градусы | нужен датчик на груди |
| MotorScore | в первой версии нет | вводить только с открытой формулой и после сверки с оценкой врача на пилоте |

### Симулятор — работа без железа

`simulate.py` берёт заданные углы (например, 3 подъёма руки до 140°), считает, что
в этот момент видят акселерометр и гироскоп каждого датчика, и добавляет то, что делает
настоящий MPU-6050: шум, смещение гироскопа, небольшой перекос крепления.
Правильный ответ известен заранее, поэтому тесты пишутся сразу.

⚠️ Поворот в симуляторе задаётся матрицей, и она обязана быть настоящим поворотом:
определитель +1. С зеркальной матрицей (−1) симулятор врёт, и правильный алгоритм
выглядит сломанным — на этом споткнулась первая проверка 24 сентября.

### Проверка точности — `validate.py`

1. `criteria.json` пишется и коммитится **до** первого замера — git покажет дату.
2. Замер: врач или инструктор выставляет гониометром угол — 0°, 30°, 60°, 90°, 120°,
   на каждом 3 секунды неподвижно. 10 здоровых добровольцев × 3 повтора.
3. Отчёт: средняя ошибка (MAE), максимальная ошибка, график Бланда — Альтмана.
4. Повторяемость: тот же человек через 10 минут, датчики сняты и надеты заново.
5. Прошли или нет — пишется как есть. Отрицательный результат тоже сохраняется.

## 3. Веб-приложение

По питчу интерфейс — на компьютере в кабинете врача. Поэтому основа — веб-приложение
в Chrome: ставить ничего не надо, работает и на Windows, и на Mac.

### Стек

| Что | Чем | Почему |
|---|---|---|
| Сборка | Vite + TypeScript | быстрый старт; типы ловят ошибки в разборе байтов до запуска |
| Интерфейс | без фреймворка | экранов шесть — React здесь лишний слой. Если кто-то в команде уже пишет на React — можно, но учить его ради проекта не надо |
| Датчики по USB | Web Serial | способы А и В: встроен в Chrome и Edge на компьютере |
| Датчики по Bluetooth | Web Bluetooth | способ Б |
| Живой график | свой `<canvas>` | 100 точек в секунду на датчик; своя отрисовка — без тормозов |
| Графики в отчёте | Chart.js | прогресс по тестам, сравнение сторон |
| Отчёт в PDF | печать браузера: `window.print()` и стили `@media print` | библиотека не нужна; «Сохранить как PDF» есть в любом Chrome |
| Хранение | IndexedDB через библиотеку `idb` | раздел 4 |
| Хостинг | GitHub Pages | бесплатно; HTTPS есть, а Web Serial и Web Bluetooth работают только по HTTPS |
| Тесты | Vitest | те же CSV, что в `lab/tests/golden/`: углы совпадают с Python до 0.1° |

⚠️ Web Serial и Web Bluetooth есть в Chrome и Edge, **нет в Safari и Firefox**.
Окно выбора устройства открывается только по нажатию кнопки — это правило браузера.

⚠️ GitHub Pages отдаёт сайт по адресу `…github.io/<репозиторий>/`. В `vite.config.ts`
параметр `base` должен совпадать с именем репозитория, иначе страница откроется пустой.

```
├── core/metrics.ts       ROM, симметрия, плавность           ← перенос metrics.py

```

Правило: экраны и отчёт сами ничего не считают — всё берут из `core/`. Тогда живой угол
и цифры в отчёте всегда сходятся.

### Фейковые датчики

`sources/fake.ts` отдаёт данные так же, как настоящие датчики. С ним пишешь всё приложение
до того, как готово железо, а потом просто меняешь источник. Второй режим — **повтор записи**:
прогнать через приложение CSV из лаборатории или из центра, как будто вживую.

⚠️ Демо-режим всегда подписан на экране «ДЕМО» и не попадает в историю детей.
Показывать фейковые данные как настоящие нельзя — ни куратору, ни жюри.

### Экраны — тест за 10–15 минут

1. **Ребёнок** — список кодов (`P07`); добавить: код, год рождения, форма ДЦП, уровень GMFCS,
   какая сторона слабее.
2. **Датчики** — подключить, проверить: все на месте, заряд, связь.
3. **Калибровка** — «сидим прямо, руки вдоль тела», полоска на 3 секунды.
4. **Тест** — движения по списку врача, каждое 3 раза на каждой стороне; на экране картинка
   движения, живой угол и счётчик повторов. Список по умолчанию (утвердить с врачом):
   подъём руки вперёд, подъём в сторону, сгибание локтя с прижатым плечом.
5. **Отчёт** — таблица «движение × сторона»: ROM, плавность, наклон туловища; симметрия;
   график ROM по прошлым тестам; кнопка «PDF». Для родителей — отдельная страница
   простыми словами.
6. **История** — все тесты ребёнка, выгрузка.

### Подключение по USB — ядро способа А

```ts
async function connectUsb(onLine: (line: string) => void) {
  // вызывать только из обработчика нажатия кнопки
  const port = await navigator.serial.requestPort();
  await port.open({ baudRate: 460800 });
  const reader = port.readable!.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = '';
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    const lines = buffer.split('\n');
    buffer = lines.pop()!;                 // последняя строка может быть недописанной
    for (const line of lines) onLine(line.trim());
  }
}
```

Строки с `#` — паспорт, остальные — отсчёты: `line.split(',').map(Number)`.
Типы для TypeScript — пакет `@types/w3c-web-serial`.

### Подключение по Bluetooth — ядро способа Б

```ts
// UUID — из контракта, строчными буквами
const SERVICE = '…';
const DATA = '…';

type Sample = { seq: number; place: number; lowBattery: boolean; raw: number[] };

async function connectBle(onSample: (s: Sample) => void) {
  // вызывать только из обработчика нажатия кнопки; каждый блок — отдельный вызов
  const device = await navigator.bluetooth.requestDevice({
    filters: [{ namePrefix: 'NM-' }],
    optionalServices: [SERVICE],
  });
  const server = await device.gatt!.connect();
  const service = await server.getPrimaryService(SERVICE);
  const data = await service.getCharacteristic(DATA);
  data.addEventListener('characteristicvaluechanged', (e) => {
    onSample(parsePacket((e.target as BluetoothRemoteGATTCharacteristic).value!));
  });
  await data.startNotifications();
}

function parsePacket(v: DataView): Sample {
  // 18 байт, little-endian — как в таблице контракта
  const raw: number[] = [];
  for (let i = 0; i < 6; i++) raw.push(v.getInt16(6 + 2 * i, true)); // ax ay az gx gy gz
  return {
    seq: v.getUint32(0, true),
    place: v.getUint8(4),
    lowBattery: (v.getUint8(5) & 1) === 1,
    raw,
  };
}
```

Типы Web Bluetooth для TypeScript — пакет `@types/web-bluetooth`.

## 4. Хранение

### Первая версия — IndexedDB в браузере компьютера

Почему не `localStorage`: там около 5 МБ и только строки, а один тест — это мегабайты сырых чисел.
IndexedDB хранит двоичные массивы и держит сотни мегабайт.

| Хранилище | Что лежит |
|---|---|
| `children` | id, имя без фамилии (или код участника, если так решил центр), год рождения, форма ДЦП, GMFCS, слабая сторона. **Без фамилии, ИИН и фото** |
| `tests` | ребёнок, дата, список движений, калибровка, версии прошивки, приложения и алгоритма, метрики, комментарий врача, признак `demo` |
| `chunks` | сырые отсчёты кусками по 10 секунд (`Int16Array`) |
| `events` | начало и конец движений, повторы, обрывы связи — с номером отсчёта |

**Объём:** 100 Гц × 5 датчиков × 12 байт ≈ 6 КБ/с → ~5 МБ на 15-минутный тест.
300 тестов — около 1.5 ГБ, компьютеру хватит.

**Сохранность:**

- Кусок пишется каждые 10 секунд: закрылась вкладка посреди теста — потеряно не больше 10 секунд.
- `navigator.storage.persist()` — просим браузер не чистить данные самостоятельно.
- Руками браузер всё равно могут очистить. Поэтому выгрузка раз в неделю: приложение
  напоминает, если прошло больше 7 дней.
- Метрики считаются из сырых данных, и в тесте записана версия алгоритма. Улучшили формулу —
  пересчитали все старые тесты. Поэтому сырые данные храним всегда.

### Выгрузка

- **CSV одного теста** — тот же формат, что в лаборатории (раздел 1), в паспорте — версия
  алгоритма `algo=`. Открывается в Excel и в `lab/`.
- **Архив всего** (библиотека JSZip): все дети и тесты одним файлом — перенести на другой
  компьютер или сохранить копию. Обратная кнопка — «Загрузить архив».
- **Отчёт PDF** — с именем ребёнка, без фамилии.

### Приватность — правила для кода

- В приложении нет фамилии, ИИН, фото и видео с лицом: ребёнок записан по имени.
  ⚠️ Изменено 17 октября 2026 решением Амирхана: было «только код `P07`», но код на экране
  читался хуже имени. Поле принимает и имя, и код: для пилота можно вписать код участника.
- Если центр работает с кодами — таблица «код ↔ ФИО» живёт только у центра, не у команды
  и не в приложении.
- Выгрузки — на устройства центра и команды, не в общие чаты.

### Позже — облако (Supabase)

Зачем: врач видит историю с любого компьютера, у команды — общая база для анализа.
Как: те же таблицы в Postgres, сырые файлы — в Supabase Storage; правило доступа
(Row Level Security) — врач видит только детей своего центра.

⚠️ Только когда центр и куратор скажут, где можно хранить данные детей. Серверов Supabase
в Казахстане нет — этот вопрос решают они, не команда.

## 5. Критерии приёмки софта — записать до проверки

| Что | Критерий |
|---|---|
| Углы на данных симулятора | ошибка < 3° с шумом и смещением |
| Перенос на TypeScript | совпадает с Python до 0.1° на тех же CSV |
| Точность на людях | MAE ≤ 5° против гониометра |
| Повторяемость | повторный тест: ROM ±5°, симметрия ±5 п.п. |
| Задержка «движение → экран» | ≤ 100 мс. Как мерить: снять руку и экран на телефон в замедленной съёмке и посчитать кадры |
| Потери пакетов (способ Б) | ≤ 1% на расстоянии 3 м |
| Надёжность | закрыли вкладку посреди теста — потеряно ≤ 10 с |
| Время теста | ≤ 15 минут вместе с надеванием датчиков |

## Словарь

| Термин | Что это |
|---|---|
| Сырые данные | числа прямо с датчика, до всякой обработки |
| Смещение гироскопа | в покое гироскоп показывает не ноль, а пару °/с; если не вычесть, угол уплывает |
| Madgwick | фильтр, который собирает полную 3D-ориентацию датчика |
| Гистерезис | два порога вместо одного, чтобы дрожание у границы не считалось событием |
| SPARC | мера плавности по спектру скорости; значения отрицательные, у плавного движения ближе к нулю |
| Web Serial | доступ сайта к USB-порту в Chrome, с разрешения пользователя |
| notify | блок сам присылает новые данные, компьютеру не нужно спрашивать каждый раз |
| UUID | уникальный номер сервиса и характеристики Bluetooth |
| little-endian | младший байт числа идёт первым |
| IndexedDB | база данных внутри браузера |
| MAE | средняя абсолютная ошибка |
| Бланд — Альтман | график согласия двух способов измерения: есть ли сдвиг и насколько велик разброс |
| Golden-тест | сравнение результата с заранее сохранённым правильным ответом |
